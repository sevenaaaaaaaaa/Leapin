## macOS 端：七个用户痛点逐项拆解

这一节是本轮复盘的重点。每一项都按「现象 → 根因 → 方案 → 验收」写清，全部来自真实使用反馈。

### M1. 添加订阅后看不到节点的链接情况 ✅ 已交付（2026-11-17）

> 落地：`GET /v1/nodes`（节点 + 组归属 + LPHealth 探测记录）、`POST /v1/nodes/test`（按名单/全部测延迟，复用 HealthProber 真实拨号路径，结果写回 LPHealth）；Profiles 页新增「节点」面板：状态点分档着色（<200ms 绿 / ≤800ms 黄 / 更高红 / 失败灰）、单行复测、全部测速；无任何探测记录时首次出现自动测一轮。DIRECT 保留为可测基线，REJECT 不参与。覆盖：ControlServer 传输测试 8 个、NodeList 引擎测试 3 个、契约 round-trip 3 个。

**现象**：导入 Clash 订阅 / base64 节点列表 / ss·trojan·vmess·vless·hysteria2 URI 之后，界面上只有配置条目，看不到每个节点是否在线、延迟多少、能不能用。用户只能"盲连"。

**根因**（代码证据）：
- `HealthProber`（`Sources/LeapinRuntime/HealthProber.swift`）确实存在，而且探测方式是走真实拨号路径的 TCP 连接（含代理握手），质量很高——但它**只服务 url-test / fallback 策略组的内部后台选择**，探测结果留在引擎内部，没有暴露到控制面 API，更没有任何 UI 展示。
- `ProfilesView` / `ImportCenter` 的职责止于"导入"，导入完成即结束，没有"节点列表"这个视图概念。

**方案**：
1. 控制面新增 `GET /v1/nodes`：返回全部出站节点的名称、类型、所属组、来源配置、最近探测结果（延迟 / 成败 / 探测时间）。
2. 控制面新增 `POST /v1/nodes/test`（支持按节点名、按组、按全部三档）：复用 HealthProber 的拨号路径，超时 4s，结果即出即回（流式或分批）。
3. `ProfilesView` 增加「节点」页签：表格列出节点 + 协议 + 延迟 + 状态（在线/超时/失败原因），单行可单独复测。
4. 延迟展示分档着色：< 200ms 绿、200-800ms 黄、> 800ms 红、失败灰。

**验收**：导入一个 ≥ 20 节点的订阅后，不做任何其他操作，30 秒内能在节点页看到每个节点的延迟与在线状态；点击任一节点"复测"3 秒内出结果。

### M2. 节点测速完全没有 ✅ 已交付（2026-11-17）

> 落地：`POST /v1/nodes/speedtest`（name / 可选 http 测速地址 / 可选 1-25MB 上限），经节点真实拨号路径下载测试对象统计吞吐量（Mbps）；`NodeSpeedTest`（LeapinNet）处理超时部分计量（≥64KB 出数、不足判死）；引擎串行化测速防争用；节点行新增 ⚡ 带宽测速按钮与结果展示。已知边界：拨号流上无法叠加 TLS，测速走明文 HTTP（默认 cachefly 100mb，可配）。覆盖：NodeSpeedTest 回环测试 4 个（字节上限/非 2xx/超时部分/超时判死）、传输测试 2 个、契约 round-trip 1 个。

**现象**：没有测速。既没有延迟测试的入口（见 M1），更没有带宽/吞吐量测试。`FloatingStatusView` 显示的是**本机当前全局流量的实时速率**，不是节点测速——两者用户很容易混淆，而前者掩盖了后者的缺失。

**根因**：全库无 throughput / bandwidth / speedtest 相关实现；只有 M1 提到的内部 TCP 连通性探测。

**方案**：
1. 延迟测速：即 M1 的 `POST /v1/nodes/test`（TCP 握手延迟 + HTTPS 首字节延迟两档）。
2. 带宽测速：新增 `POST /v1/nodes/speedtest`，对选中节点经代理链路下载一个固定尺寸测试对象（默认 10MB，可配 5/10/25MB），报告下行速率（Mbps）、峰值、抖动。测试对象 URL 可配置，默认用 Cloudflare speed 端点。
3. 结果入历史：每个节点保留最近 5 次测速记录，UI 可展开。
4. 明确区分两处文案：浮窗的"当前速率"改名「实时流量」，节点测速叫「节点测速」，避免再次混淆。

**验收**：对任一在线节点发起带宽测速，15 秒内返回下行速率数值；结果与浏览器手测同节点相差不超过 30%。

### M3. 菜单栏没有快速测速 ✅ 已交付（2026-11-17）

> 落地：菜单栏改为 window 风格面板（可放搜索框与嵌套菜单），顶部新增「当前节点 + 延迟 + 快速测速 / 全部测速」；状态栏图标直接显示最近一次延迟。**Mihomo 模式不再灰**：延迟测试改走内核 `GET /proxies/{name}/delay`（`ManagedMihomo.delay`），只有内核能拨 clash 协议；结果统一写回 `LPHealth`，Profiles 页、菜单栏、策略选择读同一个数。全部测速带 3/21 进度与「最快 XX · 42 ms」，结果留在面板与图标上（系统通知需要签名与授权，本轮未加）。覆盖：`MihomoLatencyTests`（真内核：proxies/mode/delay/503 文案/controlTestNodes/LPHealth）、`KernelProxyTests` 5 个、`MenuBarKitTests` 13 个。

**现象**：菜单栏面板（`MenuBarPanel`，`Sources/LeapinApp/LeapinApp.swift:1039`）现在只有：启动/停止代理、系统代理开关、实时浮窗开关、端口显示、页面导航。没有测速入口。

**方案**：
1. 菜单栏面板顶部加「快速测速」按钮：一键对**当前策略组正在使用的节点**跑延迟测试，结果直接显示在按钮旁（如 `香港 03 · 87 ms`）。
2. 加「全部测速」次级动作：后台跑全部节点延迟，完成后以 macOS 通知告知最优节点。
3. 测速进行中按钮转菊花，不打断面板其他操作。

**验收**：点开菜单栏图标 → 按一次快速测速 → 5 秒内看到当前节点延迟；全程不需要打开主窗口。

### M4. 菜单栏不能切换机场与节点 ✅ 已交付（2026-11-17）

> 落地：菜单栏两个菜单——「机场」列出全部配置并在当前项打勾（走 `ProfileStore` 的同一条 `activate` 路径），「节点」按策略组分组、选中打勾、右侧显示最近延迟，节点数 >15 时出现搜索框。原生模式走 `selectOutbound`；Mihomo 模式走内核 `PUT /proxies/{group}` 并持久化选择（`selectManagedPolicy`）。规则模式下「当前组」取最后一条 MATCH/FINAL 规则指向的组（`MenuBarKit.finalPolicy`），全局模式才用 GLOBAL，避免显示错的节点。覆盖：`MenuBarKitTests`（快照/搜索/最优节点/选节点持久化/finalPolicy）、`MihomoLatencyTests`（真内核选择往返）。

**附带修复 · 端口冲突检测**：启动前用 `PortAudit` 枚举本次要绑的端口（混合/HTTP/SOCKS/DNS/控制），用 `lsof` 找出占用者并标注 launchd 服务名（如 `com.user.mihomo`），有冲突直接失败并给出「谁占的、怎么让」，不再出现「在跑的监听上再绑一次、看起来启动成功」或静默卡死；同时提示另一个 mihomo 进程的存在。覆盖：`PortAuditTests` 10 个（含真实外部监听进程 + 引擎快速失败）。

**现象**：菜单栏无法切换"机场"（订阅/配置），也无法在策略组里换节点。用户每次换线路都要打开主窗口 → Profiles → 操作，链路太长。

**方案**：
1. 菜单栏加「机场」子菜单：列出全部配置（profile），当前生效的打勾，点击即切换（等价于主窗口的切换动作，走同一条 `ProfileStore` 路径）。
2. 菜单栏加「节点」子菜单：按策略组分组列出各组可选节点，当前选中打勾，点击即 `select`（复用 `/v1/policies` 已有的切换通路）。
3. 节点菜单项右侧显示最近一次延迟（来自 M1 的探测缓存），让用户"看着延迟选节点"。
4. 子菜单条目超过 15 条时按组折叠 + 顶部搜索框。

**验收**：从菜单栏完成一次"换机场 → 换节点"全流程 ≤ 3 次点击，不开主窗口；切换后主窗口（若开着）状态同步刷新。

### M5. 去广告不支持旁路模式

**现象**：`AdBlockEngine`（`Sources/LeapinPolicy/AdBlock/AdBlockEngine.swift`）已实现域名拦截 + cosmetic selectors，验证记录里 103 条规则生效。但它**只在流量经过 Leapin 代理链路时生效**——用户不开系统代理 / 不开 TUN 时，去广告完全不起作用。

**根因**：去广告判定挂在代理链路的规则解析路径上，没有"只接管 DNS、不接管流量"的轻量模式。

**方案**：
1. 新增「轻量去广告」开关（旁路模式）：只起 DNS 拦截层（本机 53 端口监听 + 系统 DNS 指向，或仅对配置了 Leapin 为 DNS 的设备生效），命中广告域名直接返回 `0.0.0.0` / `::`，不起系统代理、不开 TUN。
2. 旁路模式下去广告规则库与接管模式共用同一份 `AdBlockEngine` 数据，规则更新一处生效两处。
3. UI 明示两种模式的差异：旁路模式只能做域名级拦截（无 cosmetic 注入、无路径级规则），文案写清"域名级去广告，无需接管流量"。
4. 与接管模式互斥提示：接管模式开启时旁路开关自动置灰并说明原因。

**验收**：不开系统代理、不开 TUN，仅开启轻量去广告后，访问已知广告域名的 DNS 解析返回 `0.0.0.0`；正常域名解析不受影响；模式切换不需要重启引擎。

### M6. 反攻击加固缺失

**现象**：三个暴露面目前都没有防护：
1. **控制面**：Bearer token 一刀切，无失败限流、无来源限制告警。`allowLAN = true` 之后局域网里任何人都能试探 7900。
2. **节点侧**：节点被 QoS / 被 RST 注入 / 被封锁时，没有熔断与自动切换，用户只能手动发现"突然不能用了"。
3. **本机网络**：DNS 劫持、ARP 异常、默认路由被改（局域网攻击常见手法）没有任何检测与告警。

**方案**：
1. 控制面加固：连续鉴权失败 5 次锁定来源 IP 10 分钟；开启 LAN 监听时在设置页显著提示风险并要求二次确认；控制面访问日志（来源、路径、状态码）落盘可查。
2. 节点熔断：url-test / fallback 组复用 HealthProber 结果，连续 3 次探测失败自动标记熔断并切到次优节点，熔断节点 10 分钟后半开试探；全部熔断时发 macOS 通知。
3. 本机网络哨兵：周期性比对系统 DNS 配置、默认网关 MAC、默认路由；发现 DNS 被指向陌生服务器 / 网关 MAC 突变 / 路由表异常新增时立即通知告警。
4. 以上三条各给一个总开关，默认开（通知可关）。

**验收**：用错误 token 连续请求控制面 6 次，第 6 次收到 429 且日志有锁定记录；人为断开当前节点（如断其端口），30 秒内自动切换并在通知中心看到切换告知。

### M7. 防"我之外的中间人"窃听

**现象**：Leapin 自己有完整 MITM 能力（`MITMHandler.swift` + `CertificateAuthority.swift`），这是用户自己要的功能。但反过来——**系统里被其他工具（抓包软件、公司 MDM、恶意软件）注入了别的 CA、流量正被别人解密**——目前没有任何检测手段。用户要的是：只允许 Leapin 自己的 CA 解密我的流量，任何其他中间人被立刻发现。

**方案**：
1. **CA 审计**：扫描系统钥匙串与用户钥匙串中全部受信根证书，与已知 OS 出厂根 + Leapin 自己的 CA 比对，列出所有"第三方注入 CA"，标注来源属性（常见抓包工具 / MDM 描述文件 / 未知），未知来源红色告警。
2. **敏感域钉扎**：内置敏感域列表（银行、支付、邮箱、Apple ID），对这些域做证书链钉扎校验；发现链上出现非预期 CA（包括 Leapin 自己的——用户可白名单豁免）立即告警并可选阻断。
3. **Leapin CA 自检**：验证 Leapin CA 的私钥权限（0600、仅当前用户）、CA 使用范围标注；提供"一键吊销并重新生成"。
4. **定期巡检**：CA 审计每次启动时跑一次 + 每 24h 跑一次，结果进 Privacy 页（`PrivacyView` 已有，扩展而非新建）。

**验收**：在钥匙串手工导入一张新的受信测试 CA 后，下次巡检（或手动点"立即审计"）能在 Privacy 页看到该 CA 被列为"第三方注入"并给出移除指引；访问钉扎列表内域名时伪造证书链会触发告警。

## 移动端（iOS / Android）：三个问题 + 定位重决策

### P1. 排版有问题

**现象**：两个端的页面排版不满足日常使用：信息密度失衡、关键状态不可扫读、不同屏幕尺寸下布局破损。

**具体清单（修复时逐项核对）**：
- iOS：Dashboard 指标卡在小屏（SE / mini）挤压换行错乱；连接列表域名过长截断后无法查看全文；策略组页空状态只有一行字没有引导。
- Android：`ConsoleScaffold` 导航项 6 个以上时底栏拥挤溢出；Setup 页表单在小屏键盘弹起后遮挡输入框与提交按钮；Dark/Light 主题切换后部分卡片对比度不达标。
- 两端共同：字体档位没有经过 8pt 网格校准，列表行高、卡片间距各页不一致（没有一个统一的 spacing token 落地——桌面端的 `MobileTheme` tokens 声明了但没有在所有页面强制执行）。

**验收**：iPhone SE（375pt）与 iPad（竖屏分屏 1/2）两端各核心页面截图走查无重叠、无溢出、无错位；Android 360dp 宽度下底栏不溢出、Setup 页键盘弹起可完成全部输入；两端页面间距全部走 token，无硬编码 magic number。

### P2. 入口有问题

**现象**：1.1 已修掉"强制配对墙"（首屏改为工具页），但入口问题没有修完：
- 打开 App 后的第一屏是「工具」，而用户 90% 的意图是看 Mac 端状态——第一屏与首要意图错位。
- 「连接 Mac」的入口藏在设置里，新用户找不到；配对流程三步（填 IP、填端口、粘贴令牌）全部手输，没有扫码/ Bonjour 自动发现。
- 两端的功能入口层级不一致：iOS 用 Tab、Android 用 Scaffold 底栏但条目顺序和命名都不完全对齐，用户跨端使用要重新找一遍。

**方案**：
1. 首屏改为 Dashboard：未配对时 Dashboard 显示「未连接」引导卡（一键去配对），工具页降级为二级入口。
2. 配对流程重做：Mac 端设置页生成配对二维码（含 IP、端口、token 的一次性深链），手机端扫码即连；同时保留手动输入兜底；局域网 Bonjour 自动发现列出可用 Mac。
3. 两端信息架构对齐：同样的 4 个一级入口（状态 / 连接 / 策略 / 工具）、同样的顺序、同样的命名，设置收进右上角。

**验收**：新装 App 从打开到连上 Mac，扫码路径 ≤ 40 秒、≤ 4 步；两端一级入口数量、顺序、命名完全一致（对照表进文档）。

### P3. 产品定位有问题（重决策）

**现状定位**（`docs/MOBILE.md`、`CLAUDE.md` 明确写死）：手机端是**控制台 / 诊断端**，不是 VPN——读 Mac 控制面状态、执行动作，不代理手机流量。系统级接管需要 NetworkExtension（iOS）/ VpnService（Android），当前都不包含。

**用户反馈**：这个定位无法满足正常使用。

**分析**：控制台定位成立的前提是"用户 Mac 常开 + 手机和 Mac 在一起"。真实场景里手机离开局域网就是一块砖：看不到状态、执行不了任何动作。它只对"Leapin 重度桌面用户"是加分项，对"想要手机能用的用户"是不合格产品。两个定位服务的不是同一群人，现在的产品是两头不靠。

**候选方案**：

| 方案 | 内容 | 成本 | 风险 |
|------|------|------|------|
| A. 保持控制台 | 只修 P1/P2，定位不动 | 低 | 用户反馈已否定，等于不做 |
| B. Android 先做独立 VPN | VpnService + 内嵌 Mihomo 内核（ClashMetaForAndroid 成熟路径），手机流量自理；控制台能力保留为第二 Tab | 中 | 内核体积 + 电量；Google Play 外分发无政策障碍 |
| C. iOS 独立 VPN | NetworkExtension Packet Tunnel + 内嵌 sing-box/Mihomo | 高 | **硬前提：付费开发者账号**（NetworkExtension 权限必须），当前仓库没有账号配置；签名后 TestFlight 分发 |
| D. 双端定位重构 | Android 走 B 先行；iOS 走 C 排期（账号就绪后），此前 iOS 保持控制台并修 P1/P2 | B 中 + C 高 | 两端定位短期不对称，文案需写清 |

**推荐：D**。理由：Android 无账号硬门槛，VpnService 路径成熟，最快把"手机能用"做实；iOS 的 NetworkExtension 是账号问题不是技术问题，先把账号申请提上日程，账号到位前继续交付修好的控制台。

**决策点（需确认）**：① 是否注册 Apple 付费开发者账号（$99/年，决定 iOS 路线是 C 还是停在控制台）；② Android 独立 VPN 的内核选型（推荐 Mihomo，与桌面端受管内核一致，规则复用）。

**验收**（B 部分）：Android 端不连 Mac 的情况下，导入订阅 → 开启 VPN → 手机浏览器访问验证 IP 已走节点；断流自动重连；控制面 Tab 功能不回退。

## 对标 Surge：缺口与优势总结

### 最常用的缺口（改流量工具链）

- 流量统计持久化（数据结构有，无 UI）
- 日志/事件中心（API 完整，UI 弱）
- 抓包会话库（仅 HAR 导出）

### 本轮新增缺口（日常使用每天都碰到）
- 节点可见性 + 测速（M1/M2）—— 这是 Surge / Clash 系客户端的**底线能力**，我们缺席

- 旁路去广告（M5）—— AdGuard 类工具的标准形态

### 我们的独有优势
- 远端控制（iOS/Android 原生控制台 + HTTP API）
- 开发工具链完整（CLI 全功能、CI 自动化）

## 高层总结

**现状：** 最近三个版本做了四个关键事（浮窗、重写、脚本、移动修复），但其中三个（重写/Mock/临时规则）已完成但还没 merge。加上脚本后端完成但 UI 缺失。

**缺口（修订）：** 之前只盯着"对标 Surge 的功能差"，漏了更基础的——**节点不可见、测速不存在、菜单栏不能干活、移动端定位不成立**。这些是用户每天第一分钟就碰到的东西，优先级高于一切对标功能。

**优势：** 远端控制能力（iOS/Android + API）是 Surge 付费才有的东西，而你已经标配了。应该加深而不是分散。

**建议（修订）：** v1.12/v1.13 把节点可见、测速、菜单栏三件套做透（macOS 端口碑翻盘）；v1.14 安全三件套做成差异化；v1.15 移动端要么不做、要么做成能用的（Android 先独立 VPN，iOS 等账号）。脚本平台和历史回溯顺延到 v1.16/v1.17，不影响主战场。
