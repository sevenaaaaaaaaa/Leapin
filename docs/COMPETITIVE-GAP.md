# 竞品功能对标与路线规划

> 对照对象：Surge iOS 的功能入口（用户提供的 9 张截图）。
> 我们的现状一律以本仓库代码为准，每条都标了出处，便于核对。
> 结论先行：**我们不缺骨架，缺的是"改流量"和"看历史"这两块；而远端控制这块我们比 Surge 做得更完整。**


## 修订记录

### 2026-11-15（用户反馈后修订）

两处判断被推翻，原文保留以便对照：

1. **小组件 / 实时浮窗**：原文放在「C. 暂不做」，理由写的是"平台或场景不匹配"。**这个判断是错的。**
   常驻型工具的窗口平时是关着的，小组件与浮窗才是产品持续存在的地方；把它归为装饰性需求，等于放弃了日常接触点。
   改为**必做**（见下方修订路线）。
2. **脚本（JavaScript）**：原文放在「待评估」，理由是"实现成本最高"。**排序逻辑错了。**
   重写只能表达静态规则，脚本能表达逻辑，两者能力上限差一个量级；成本高应该影响"何时做"，不影响"是否做"。
   改为**一等能力**，紧随重写落地。

同时修正一处工程判断：**macOS 小组件不是纯 UI 成本**。桌面端目前由 `scripts/build-app.sh` 用 SwiftPM 构建后手工组装 bundle，
而 Widget Extension 必须以 `.appex` 形式嵌入，现结构支持不了 —— 要先把 macOS 打包迁到 Xcode 工程。
iOS 侧已有 xcodegen 工程，小组件成本低得多。

### 2026-11-15（第二次修订：撤回"暂不做"清单）

**撤回上一版的 C 节。** 把 pcap、代理链、主动探测、tvOS、混合网络、热点代理、DDNS、主题机制
列进"暂不做"，是我用实现成本否决了产品方向——这是越权。这些不是"该不该做"的问题，
是"什么顺序、什么前置"的问题。

**根因不是功能难，是架构不同。** Surge 从 L3 隧道起家，我们是 L4 代理起家：

| 事实 | 证据 |
| --- | --- |
| 我们的数据面是本地端口上的 L4 代理（CONNECT 转发） | `ProxyServer.swift` 用 `NWListener` 起本地监听 |
| 我们没有常驻特权 helper，也没有 utun | 全仓库无 `SMAppService.daemon`；`ManagedTUN` 只导出 mihomo 启动包给终端 |
| 我们没有 NetworkExtension | 无 `NetworkExtension` 引用 |

所以同一项能力，在隧道架构下便宜、在代理架构下昂贵：

| 能力 | 现状（L4 代理）成本 | 隧道（L3）下成本 | 说明 |
| --- | --- | --- | --- |
| pcap 抓包 | **XL**：要 BPF（root）或 `tcpdump` 子进程 | **S**：隧道里本来就有 IP 包，写 pcapng 即可 | 这是差距最大的一项 |
| 混合网络（Wi-Fi+蜂窝并发） | **XL**：要 MPTCP / 多路径选路 | **L**：路由可选路，仍要处理粘滞与回退 | iOS 能力，需 NE |
| 个人热点代理 | **L**：要常驻 + 给热点客户端提供代理 | **M**：隧道天然覆盖接入的客户端 | iOS 能力，需 NE |
| 代理链 | **M**：`OutboundDialer` 支持嵌套拨号 | **M**：同左 | 与架构无关，纯协议组合 |
| 主动探测（NAT / 带宽） | **M**：STUN 式探测 + 吞吐测试 | **M**：同左 | 与架构无关 |
| DDNS | **S**：域名 API + 定时上报 | **S**：同左 | 与架构无关 |
| tvOS 端 | **L**：新 target + 复用控制台 | **M**：tvOS 17 起支持 NE，可做完整端 | 与架构相关 |
| 主题机制 | **S**：设计令牌外部化 | **S**：同左 | 与架构无关 |

**结论：想让这些都变便宜，主线是"把数据面从代理升级成隧道"，而不是逐项硬啃。**
这也解释了为什么 v1.11 / v1.12 先做重写与脚本：它们不依赖数据面，属于并行的低风险收益。

## 一、结论

1. **代理与分流骨架已经齐了**：原生内核 + Mihomo 受管内核、六类规则、三种策略组、DoH/DoT、去广告、MITM 抓包、控制面 API。Surge 在这层的核心能力我们不落后。
2. **真正的缺口集中在两类**：
   - **改流量**：脚本（JavaScript）、HTTP 重写 / Mock、模块覆盖层、临时规则。Surge 把这些当成日常工具，我们一条都没有。
   - **看历史**：流量统计、日志簿 / 事件中心、抓包会话库。我们现在只有"此刻"，没有"过去"。
3. **我们的独有优势是"远端控制"**：Surge 把它列为付费功能（远端控制器 / 云通知 / HTTP API / Web 面板），而我们已经有两端 App + 完整控制面。这条应该继续加深，不该分散去抄它的 tvOS 或小组件。

## 三、分层建议

### A. 必须补齐（缺的就是日常会用到的）

按"每天都会用到"排序，而不是照抄对方的付费清单：

1. **HTTP 重写 + Mock**（含重定向、改 header/body）—— 调试与联调的高频刚需，且我们已有 MITM 管道，改造成本最低。
2. **脚本（JavaScript）**—— 重写解决 80% 场景，脚本解决剩下 20%（动态逻辑）。放第二批，因为它要引入 JS 引擎与沙箱边界。
3. **临时规则** —— 成本极低（规则引擎已有），收益立刻可见：看到一条连接，就地加规则。
4. **日志簿 / 事件中心** —— 后端已有 `/v1/events` + audit，缺一个界面把它讲清楚。
5. **流量统计持久化** —— 需要落盘与聚合，工作量中等，但对"这个月谁在偷跑流量"这种问题无可替代。
6. **抓包会话库 + 数据预览** —— 把现在的"导出 HAR"升级为"存着、能翻、能看 JSON/图片"。

### B. 应该加强（已有但薄，加强性价比高）

1. **规则分析上界面**：把 `--diagnose`（永不命中的规则）和 `--measure`（p50/p95）搬进 App，附命中计数。
2. **控制面开到局域网 + 只读 Web 面板**：现在手机要连必须先手动开 `allowLAN`，且没有浏览器可用的面板。这是我们把"远端控制"优势变现的关键一步。
3. **云通知**：连接异常 / 引擎崩溃 / 规则报错推送到手机。手机端已经在了，只差推送通道（可用 Bark / ntfy / Telegram Bot，不依赖自建服务）。
4. **配置管理**：副本、关联配置、文本模式编辑、系统分享面板。属于打磨，但用户会直接感知。
5. **MITM 能力**：HTTP/2 支持确认、body 上限可调、按域名白名单、CA 安装引导。

### C. ~~暂不做~~ → 已撤回

本节原有内容（把 pcap、代理链、主动探测、tvOS、混合网络、热点代理、DDNS、主题机制列为"不做"）
已于 2026-11-15 第二次修订时整节撤回。理由见文首「修订记录」：判断该不该做不是我的权限，
这些能力全部纳入路线（见第四节），差别只在顺序与前置。

## 五、我们相对 Surge 的取舍原则

1. **不按付费清单抄**：Surge 用订阅把功能切成卖点，我们的优先级按"日常使用频率 × 实现成本"排。
2. **把已有优势做深**：远端控制与多端一致是我们的护城河，优先级高于补齐它的边缘功能。
3. **每一版都要能演示**：验收标准写成用户能自己点一遍的动作，不写"完成 XX 模块"。
